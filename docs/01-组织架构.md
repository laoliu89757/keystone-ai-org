# 组织架构：磐石软件（Keystone Software）

版本 v1.0｜2026-10-21｜配套《AI Agent 研发工作流规范：角色、权限、AGENTS.md 与 CI 门禁》v1.0

> 本仓库把一次软件开发当成一家公司运转：**人 = 董事会**（只在不可逆处签字），**CEO = 编排 Agent**，其余 16 个岗位是被 CEO 雇佣的执行 Agent。每个岗位都有：一个名字、一张角色卡（`docs/roles/`）、一个 Paseo Agent 配置（profile）、一份权限边界、一套验收标准。

           DBA 数据库管理员  QA 测试工程师

**汇报线三条铁律**

1. **只有 CEO 派单**。任何执行者不接受"另一个执行者"的直接指令；横向通信只能提问/请求协助，且必须抄送 CEO。
2. **质量部独立**。评审官、安全官、评测官、内容质检总监对 CEO 直报，**不属于技术部**，其结论对技术部有否决权；且必须与开发线使用**不同模型家族**。
3. **人对 CEO**。执行者不许越级找人，只能升级给 CEO，由 CEO 整理后按【背景/已尝试/阻塞点/可选方案/建议】格式上报。

**Provider 变体说明**：表中模型写成基础 Provider（`claude` / `pi`）+ 模型 ID。实际 profile 里用的是**降权变体**——CEO 用 `claude-lead`，其余 Claude 岗位用 `claude-worker`，Pi 岗位用 `pi-worker`。变体通过 `extends` 继承原 Provider，只是裁掉 `create_agent` 等工具。校验脚本会自动把 `-lead` / `-worker` 归一化后再比对。

**"worker 组"** = `create_agent`、`create_schedule`、`create_heartbeat`、`kill_agent`、`archive_agent`、`archive_workspace`、`respond_to_permission`、`update_agent`、`set_agent_mode`、`create_terminal`。含义：**执行者不能自己招人、不能给自己批权限、不能给自己换模型、不能自我升级模式**。

### 模型分工的三条硬约束

1. **开发线统一在 claude 家族**（后端/算法/前端/DBA/QA/CPO/架构），保证代码风格与工具调用行为一致。
2. **质量部的三个裁判换家族**：评审=GLM、安全=DeepSeek、评测/内容质检=Gemini。与开发线不同源，避免同源盲点。
3. **CEO 与架构师用 high 思考**，事务性岗位（值班/文档/质检）用低思考或便宜模型，控制成本。

### 模型可用性台账（2026-10-21 实测）

派单前若不确认就选错模型，会得到一条 `error` 的 Agent 和一堆浪费的时间。本表是已用 `paseo run` 逐个探活的结果：

| 模型 | 状态 | 备注 |
| --- | --- | --- |
| `claude/claude-opus-5-5`（claude-lead / claude-worker） | ✅ 可用 | 开发线 + CEO + 合规 |
| `pi/9router/ag/gemini-3.8-flash` | ✅ 可用 | 便宜、长上下文；体检/质检/值班/文档/幕僚长 |
| `pi/local/raccoon/sn-glm-5-3` | ✅ 可用 | GLM 家族；独立评审 |
| `pi/local/loomy/GLM-5.3-Flash` | ✅ 可用 | GLM Lite；SRE |
| `pi/9router/amd/DeepSeek-V4-Flash` | ✅ 可用 | DeepSeek 家族；安全官 |
| `pi/shouer/sensenova-6-8-flash` | ✅ 可用 | 备用池（中文内容质量任务） |
| `pi/local/raccoon/sn-deepseek-v4-1-flash-1017` | ⚠️ 可用但慢 | 备用 |
| `pi/9router/codecraft/deepseek-v4-pro-0813` | ❌ 429/凭据错误 | 原定评审模型，已换掉 |
| `pi/9router/cbcn/deepseek-v4-flash` | ❌ 凭据错误 | — |

> 模型额度是消耗品：若某模型 429/额度上限，按「换同岗位备选 → 降级到 `pi/9router/ag/gemini-3.8-flash` → 升级给人」三级处理，**不得**因此降级门禁。

## 4 部门的"业务语言"

| 部门 | 对内的说法 | 实际负责 |
| --- | --- | --- |
| 总裁办 | 立项、派单、验收、发布决策、复盘 | 任务拆分、调度、汇总、升级、里程碑报告 |
| 产品部 | 客户要什么 | 用户故事、验收标准、`docs/requirements/` |
| 技术部 | 怎么造 | 架构与契约、四大模块实现、数据库 |
| 质量部 | 能不能发 | 测试覆盖、独立评审、安全、评测回归、内容正确性 |
| 交付运维部 | 怎么发、发完好不好 | CI/CD、环境、灰度、监控告警、值班诊断 |
| 支持与治理 | 说清楚、不出事 | 文档同步、合规清单 |

## 5 人在这个组织里的位置

人（项目负责人）不是"审批一切"，只批 8 类**不可逆**事项：

生产发布 · 生产数据库迁移 · 密钥/账号/权限变更 · 付费服务与预算 · 学生数据外发或换模型供应商 · 删除数据 · 合规结论 · 门禁与流水线变更（含评测基线）。

除此之外（单个 PR 评审合并、测试环境部署、依赖小版本升级、文档与变更日志、常规缺陷修复）**全自动**，人只在里程碑看一份验收报告。

## 7 一份任务在组织里的流转（30 秒版）

```
人 → CEO 立项
CEO → CPO 出验收标准（一切开工的前提）
CEO → 首席架构师 定契约（跨模块必做，先合契约再并行）
CEO → 并行派工：backend / ai / fe / dba（各自 worktree，各自分支）
        ↓ 各自跑本地检查 + CI
CEO → 独立评审官（同 worktree，新会话，跨家族）→ 通过 / 需修改 / 否决
        ↓ 需修改：steer 回原开发（≤3 轮）
CEO → 安全官 + 评测官（按触发条件）
CEO → 平台门禁自动合并（受保护路径 → 找人）
CEO → SRE 发测试环境 → 值班工程师观察 → 人批准生产
CEO → 里程碑验收报告 + 复盘
```

细节见 `docs/02-协作协议.md`。
