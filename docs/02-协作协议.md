# 协作协议（Agent 之间怎么干活）

版本 v1.0｜2026-10-21｜读者：CEO、幕僚长、全体岗位

> 一句话：**CEO 单点派单 → 执行者在自己的 worktree 干 → 自动通知回报 → 独立评审官否决或放行 → 平台门禁合并 → CEO 汇报董事会。**
> 任何"绕过 CEO 的两个执行者自行商量着改代码"都属于违规协作。

---

## 1 状态机（一张任务单的完整一生）

```
queued ──派单──> assigned ──开工──> in_progress ──交付──> in_review
                                        │                   │
                                        │ 卡住               ├─通过──> merged ──> verified
                                        ↓                   ├─需修改─> in_progress（≤3 轮）
                                     blocked ──升级──> escalated ──人裁决──> queued/closed
                                                            └─否决(3次)─> escalated
```

| 状态 | 谁负责推进 | 判据 |
| --- | --- | --- |
| `queued` | CEO | 已拆到"可独立验证"，有验收标准 |
| `assigned` | 执行者 | 已 `create_agent` 且 initialPrompt 含任务单 |
| `in_progress` | 执行者 | 分支有提交，CI 在跑 |
| `in_review` | 独立评审官 | PR 已开，评审官拿到 agentId |
| `merged` | 平台门禁 | 必需检查全绿 + 1 个审批 |
| `verified` | CEO | 测试环境冒烟通过 / 里程碑报告已出 |
| `blocked` / `escalated` | CEO | 命中升级条件，人已收到【背景/已尝试/阻塞点/可选方案/建议】 |

**CEO 维护状态的方式**：不需要数据库，用一张 Markdown 看板 `docs/board/<里程碑>.md` + `list_agents`（必要时）+ 完成通知。**禁止轮询**（官方明确不要 poll）。

## 2 派单协议（CEO 唯一的生产动作）

### 2.1 派单前必做三件事

1. `list_profiles` → 读每个 profile 的 `notes`，选岗位。没有合适 profile 时告诉人，不许瞎猜模型。
2. 判断**要不要 worktree**：
   - 会写文件 → worktree（`create_workspace`，`isolation: worktree`，`mode: branch-off`，`branchName: agent/<code>/<任务号>`，`baseBranch: origin/main`）
   - 只读（调研/评审/安全审计/质检/值班诊断）→ 不开，直接在 CEO 当前工作区起 Agent
3. 判断**是否可并行**：见 §4 并行规则。跨模块共享契约未合并时，**不许** fan-out。

### 2.2 派单模板（initialPrompt，逐项填满，缺项=派单失败）

```markdown
你是「<中文职位>」（代号 <code>）。你是<公司名>的<一句话职责>。

第一步（不做完不许动手）：
1. 读 AGENTS.md，记住第 4 节通用规则与第 5 节完成定义。
2. 读 docs/roles/<序号>-<code>.md，这是你的岗位说明书，你的权限边界以它为准。
3. 用一句话复述：你的任务、可写目录、验收标准。复述不对就停下来问 CEO。

任务单
- 编号：<T-编号>
- 目标：<一句话，可验证>
- 验收标准：<1..n，每条都能被检查>
- 允许修改：<目录/文件>
- 禁止修改：<受保护路径 + 他人目录>
- 依赖与契约：<openapi/schema/adr 链接>
- 命令：<本地必须跑通的检查命令>
- 预算：重试 ≤3 轮；时间 ≤<N> 小时；token ≤<N>

工作区：<worktree 路径>，分支 <agent/<code>/<任务号>>。分支已建好，直接干活。
启动模式：settings.modeId = "bypassPermissions"（否则未加白命令会被静默拒绝，你会空转）。
微任务协议：不要憋大招。先落 3–5 行骨架保存，再逐段替换；一次工具调用只做一件事；长输出分段写。
不要探针循环：先动手，最多做 1 次验证。
完成定义：见 AGENTS.md 第 5 节 + 你角色卡第 9 节。

交付要求（按顺序）：
1. 提交到你的分支并 push；
2. 在 PR 描述里逐条对应验收标准；
3. 用 templates/status-report.md 的格式回我一条回执（含：做了什么/证据/未解决/需要谁）。
禁止：合并到 main、改受保护路径、动别人的目录、跳过任何测试。
```

### 2.3 派单的三种力度

| 场景 | 工具 | 行为 |
| --- | --- | --- |
| 新任务 | `create_agent`（带/不带 workspaceId） | 起一个新岗位 Agent |
| 同一任务追加要求 | `send_agent_prompt`，`activeTurnBehavior: steer`（默认） | 插进它当前这一轮，保留上下文，最省 |
| 发现方向错了 | `send_agent_prompt` + `interrupt` 或 `cancel_agent` | 停当前轮，**保留 Agent**，再 steer 新方向 |
| 人要亲自接管/换模型 | `update_agent`（CEO 专属） | 换模型/模式/思考级别，不重开会话 |
| 任务废了 | `archive_agent` | 软删，留历史 |

## 3 回执协议（执行者 → CEO）

执行者交付时必须发一条结构化回执（模板 `templates/status-report.md`）：

```markdown
【任务】T-014 订单接口幂等
【状态】完成 / 需修改后重提 / 阻塞
【产出】分支 agent/backend/T-014 → PR #123；改动 412 行
【验收对应】1) 重复提交只产生一条订单 — 见 tests/OrderIdempotencyTest::testDuplicate ✅ …
【证据】本地 phpunit 全绿；CI 链接；覆盖率 84%
【未解决/风险】…
【需要谁】需要 DBA 补一条唯一索引任务（不允许我自己改 migrations/）
【预算消耗】2 轮 / 1.5h
```

**回执硬要求**：必须有"证据"栏（命令 + 输出摘要 + 链接）。没有证据的"我完成了"一律视为未完成，CEO 直接驳回。

## 4 并行与 worktree 规则

| 规则 | 内容 |
| --- | --- |
| R1 | 一任务一分支一 worktree：`agent/<code>/<任务号>`，`baseBranch` 明确写 `origin/main` |
| R2 | **同目录不并行**。两个任务要改同一目录 → CEO 串行，或拆成"先契约后实现" |
| R3 | 契约先行：跨模块改动必须由首席架构师先合 `openapi.yaml`/`schemas/`，再 fan-out 给前后端 |
| R4 | 只读任务共用工作区，不需要 worktree（探索、评审、审计、巡检） |
| R5 | 评审者与被评审者用**同一个 worktree**（评审者要看到真实文件），但用**新会话 + 不同 Provider 家族** |
| R6 | worktree 用完由 CEO `archive_workspace` 收尾；分支删不删由人决定，Agent 不删共享分支 |
| R7 | 一个 worktree 里只允许一个"写入者"，其他角色只读 |

MCP 写法：

```javascript
// 建隔离工作区（写代码任务）
create_workspace { isolation: "worktree", mode: "branch-off",
  branchName: "agent/backend/T-014", baseBranch: "origin/main" }
// 在该工作区起后端工程师
create_agent { title: "后端工程师 · T-014", provider: "claude-worker/claude-opus-5-5",
  workspaceId: "<wid>", settings: {...}, initialPrompt: "<§2.2 填好的模板>" }
```

CLI 等价：

```bash
paseo workspace create --isolation worktree --mode branch-off --new-branch agent/backend/T-014 --base origin/main
paseo run --provider claude-worker/claude-opus-5-5 --workspace <wid> "<prompt>"
```

> ⚠️ Windows 本机坑：给执行者传的 worktree 路径必须是绝对路径；不要传与父会话相同的 cwd（会产生双拼路径导致启动失败）。

## 5 评审循环（质量部的核心机制）

```
执行者交付 ──> CEO 起独立评审官（同 worktree、新会话、跨家族、只读）
                    │
                    ├─ 通过 ──> CEO 验证 DoD ──> 交给平台门禁合并
                    ├─ 需修改 ──> CEO steer 回原执行者（≤3 轮）
                    └─ 否决 ──> 记录否决理由；第 3 次否决 → 升级给人
```

**评审官的独立上下文保证**

- 必须 `create_agent` **新会话**，不得在开发者的会话里"顺便看看"。
- 必须不同模型家族（claude 开发 → DeepSeek 评审）。
- 只读：不 `git add/commit`、不改文件；发现小问题写成评论，不改。
- 输出固定四段：**结论（通过/需修改/否决）/ 阻塞问题 / 建议项 / 风险等级（低/中/高）**。

**评审清单**（角色卡 08 有全文，此处摘要）：验收标准是否逐条满足、是否越界、是否绕过门禁、权限与注入、幂等/并发/降级、迁移风险、测试是否真覆盖、领域约束。

**其他裁判的触发条件**

| 岗位 | 何时必须上场 | 门禁 |
| --- | --- | --- |
| 安全官 | 改依赖、改鉴权、改支付、任何对外接口、每天一次的依赖扫描 | 高危及以上 = 阻断 |
| 评测官 | 改 prompt / 路由 / 引擎 / 判定阈值 / 评测集 | 指标降幅超阈值或硬性项失败 = 阻断 |
| 内容质检总监 | 每批内容发布前按比例抽检 | 通过率低于阈值 = 阻断 |
| QA | 每个功能 PR（写测试）/ 每次发布前回归 | 覆盖率与关键路径 E2E |
| 合规官 | 涉及备案、隐私、平台政策、数据外发 | **结论必人批** |

## 6 通信矩阵

| 方向 | 允许 | 工具 | 说明 |
| --- | --- | --- | --- |
| CEO → 全体 | ✅ | `create_agent` / `send_agent_prompt` / `cancel_agent` / `update_agent` | 唯一派单权 |
| 执行者 → CEO | ✅ | 完成/错误/权限请求**自动通知**；提问用回执 | 不需要额外工具 |
| 执行者 ↔ 执行者 | ⚠️ 仅"提问/请求协助" | `send_agent_prompt` + 对方 agentId | 必须把结论抄回 CEO；**禁止**互相改对方分支的代码 |
| 执行者 → 人 | ❌ | — | 必须经 CEO 转换成升级单 |
| 执行者 → 招新 Agent | ❌ | （`create_agent` 已从 worker 组禁用） | 人手不足由 CEO 决定 |
| 执行者 → 批准自己的权限请求 | ❌ | （`respond_to_permission` 已禁用） | 只有 CEO 或人可批 |

**横向通信用法**：CEO 在 UI 右键对方标签页「复制 Agent ID」，把 ID 交给需要的岗位：

> 用 Paseo 向 Agent `<id>` 发送：「请确认 T-014 是否修改了 `orders.updated_at` 的语义；我只问不改。」

**交接口径**（`/paseo-handoff` 或手写）：接收方必须能独立开工 —— 相关文件路径、当前进展、已做的决策及理由、约束、验收标准、下一步建议。缺任何一项，接收方有权退回给 CEO。

## 7 预算与熔断（不许空转）

| 维度 | 默认上限 | 超限动作 |
| --- | --- | --- |
| 重试/返工 | 3 轮 | 停，升级 CEO |
| 评审否决 | 3 次 | 停，升级人（说明分歧点） |
| 时间/任务 | 按任务单（默认 4h） | 停，回报已完成部分 |
| token/任务 | 按任务单 | 停，回报 |
| 同一错误重复 | 2 次 | 停，换方法或升级 |

**升级单格式（固定五段，缺段退回）**：
`【背景】` `【已尝试】` `【阻塞点】` `【可选方案与影响】` `【建议】`

## 8 长任务与周期性工作

| 场景 | 机制 | 写法 |
| --- | --- | --- |
| CEO 拖着长任务，需要定期自己推一把 | `create_heartbeat`（同一个 CEO 会话，保留上下文） | 「每 20 分钟检查 T-014 进展，推进一个最小步骤，完成后删除本 heartbeat」 |
| 值班巡检（每天要新 Agent、要留历史） | `create_schedule`（每次新 Agent） | 「工作日 09:30 巡检错误率/延迟/掌握通过率/成本，出报告，异常升级 CEO」 |
| 评审/发布批处理 | `create_schedule` + `maxRuns` | 用完即停 |

**禁止**：sleep/轮询循环、`tail -f` 日志、反复读 session 文件等结果。通知会自己来。

## 9 冲突仲裁（CEO 的五个裁决）

| 冲突 | 裁决 |
| --- | --- |
| 评审官说"需修改"，开发说"你错了" | CEO 让双方各写 3 条理由 → 若涉及规范歧义，交首席架构师裁（技术）或 CPO 裁（需求）；仍不一致 → 升级人 |
| 两个任务要改同一文件 | 串行；后一个基于前一个的分支 rebase 后再开工 |
| 执行者想扩大范围 | 拒绝。范围变更必须由 CPO 更新验收标准 + CEO 重开任务单 |
| 契约与实现不一致 | 以已合并的契约为准；要让契约让步 → 首席架构师出 ADR + 人批 |
| 门禁一直红但"本地是绿的" | 以 CI 为准；SRE 排查环境差异，不许在 PR 里放宽阈值 |

## 10 一次标准里程碑的完整编排（可直接照做）

```
1  人：给 CEO 一段需求
2  CEO：拆成 N 张任务单，写 docs/board/M1.md 看板
3  CEO → CPO：出用户故事 + 每条可测的验收标准
4  CEO → 首席架构师：定接口契约 / 数据模型，出 ADR（如需）
5  契约合并后，CEO 并行 fan-out：
     create_workspace(worktree, agent/backend/T-01x) → 后端工程师
     create_workspace(worktree, agent/ai/T-01y)      → 算法工程师
     create_workspace(worktree, agent/fe/T-01z)      → 前端工程师
     create_workspace(worktree, agent/dba/T-01w)     → DBA
6  每个执行者：本地检查 → push → PR → 回执
7  CEO 收到完成通知 → 起独立评审官（跨家族、同 worktree）→ 通过/需修改
8  需修改：steer 回原执行者，≤3 轮
9  触发安全官 / 评测官 / 内容质检总监（按 §5 条件）
10 平台门禁自动合并；受保护路径 → 人批
11 SRE 部署测试环境 → 值班工程师冒烟 → CEO 汇总
12 人批准生产（唯一必需人工点之一）→ SRE 灰度 → 值班观察
13 CEO 出里程碑验收报告（templates/milestone-report.md）+ 复盘 3 条改进
```

## 11 变更分级与轻量路径（CEO 派单前必做的第一件事）

> 不是每个改动都抡得上 17 席。**CEO 必须在任务单第一行声明 `tier` 与理由**；声明与小改动准入条件不符，视为流程违规。

### 11.1 定级自检（逐条问，命中即定级）

| # | 问题 | 命中 |
| --- | --- | --- |
| 1 | 动支付 / 权限 / 权益 / 密钥 / 受保护路径？ | → **T3** |
| 2 | 新模块、新目录、或首次建立某类文件（如首次写 tests/）？ | → **T3** |
| 3 | 跨模块（如前后端同时改）或改对外契约 / Schema / 数据模型？ | → **T2 以上（含 T2）** |
| 4 | 有数据库迁移 / 数据回填？ | → **T2 以上** |
| 5 | 动 prompt / 模型 / 路由 / 判定阈值 / 评测集？ | → **T2 以上（且必跑 eval-gate）** |
| 6 | 改动 > 100 行，或涉及 > 3 个文件，或新增依赖？ | → **T2 以上** |
| 7 | 只改文案 / 注释 / 文档错字，不碰代码行为？ | → **T0** |
| 8 | 以上都不命中（单点 bugfix、局部样式、模块内部小调整） | → **T1** |

### 11.2 四级的必做与可省

| tier | 典型场景 | 必做（不可省） | 可省 | 时间盒 | Agent 数 |
| --- | --- | --- | --- | --- | --- |
| **T0** 文案 | 错字、注释、说明补充、只改 `docs/` 非受保护部分 | 改动人（writer 或原岗位）+ 人抽查 | CPO、CTO、QA、rev | ≤ 10 min | 1 |
| **T1** 小改 | 单点 bugfix、局部样式、模块内部调整（≤100 行、无契约/迁移/prompt） | 开发岗 + **独立评审官（轻审：只看 diff + 复现测试）** | CPO（任务单直给验收标准）、CTO、QA（开发自带回归用例）、eval、sec（除非动依赖/鉴权） | ≤ 30 min | 2 |
| **T2** 常规功能 | 单模块新功能、加一个接口、加一组页面、改一处判定规则 | CPO（验收标准）+ 开发岗 + QA + rev | CTO（无契约变更时）、DBA、sec、eval（未命中第 4/5 条时） | ≤ 90 min | 3–5 |
| **T3** 高风险/首发 | 新模块、跨模块、契约变更、迁移、支付/权限/权益、模型或阈值变更 | 全链路：CPO + CTO + 多开发岗 + DBA + QA + rev + sec（+ eval / editor / sre 按触发） | 无人可省 | ≤ 4 h | 5–9 |

### 11.3 任何 tier 都不能省的三件（硬保留）

1. **受保护路径 → 人批**（`.github/`、`.paseo/`、`.claude/`、`AGENTS.md`、`CODEOWNERS`、`evals/baseline/`）。
2. **迁移必须有回滚演练**（哪怕只有一行 DDL）。
3. **密钥扫描 + PR 体量检查**（平台门禁，与 tier 无关）。

### 11.4 CEO 的自律条款

- 派单首行写：`tier: T1 · 跳过 CPO/CTO，理由：单点 bugfix、无契约变更、改动 12 行`。
- 回执里回报：`tier 判定 + 实际耗时 + 实际 agent 数`，供后一次校准。
- **不得以“省流程”为名跳过 rev**（T0 除外）；不得以“这是个特例”为名把 T3 降为 T1。
- 拿不准就升一级（宁可多一个 QA，不要少一个评审）。
- **T1 的准入硬条件**：验收标准必须能由任务单直接给出且可执行（无需 CPO 转写）。写不出可执行标准 = 不是 T1，退回 T2。
- **T1 的评审走轻审路径**（见 `docs/roles/09-rev.md` §7.5）：看 diff + 复现测试 + 简短四段，不写报告文件。
- 回执必须含「被拒/被拦命令次数」——大于 0 说明遇到了权限或钩子拦截，CEO 要先查原因再决定是否重派。
- 同一类改动连续三次都走 T1，就把流程写进对应岗位卡，不必每次重新论证。

### 11.5 成本直觉（给业主看）

| 场景 | 现在这轮（T3 首演） | T1 小改 |
| --- | --- | --- |
| Agent 数 | 5（CPO/CTO/AI/QA/REV） | 2（开发 + 评审） |
| 端到端 | ≈ 80 分钟 | ≈ 10–20 分钟 |
| 人工打扰 | 0（bypass） | 0（bypass） |
| 交付物 | 模块 + 契约 + ADR + 测试 + 评审 | 提交 + 一行测试 + 评审结论 |

## 12 违规清单（出现即视为流程失败，必须复盘）

1. 执行者自己合并到 main、自己批自己、自己换模型提权。
2. 两个执行者绕过 CEO 互相改代码。
3. 为了让 CI 变绿而改阈值、删测试、加 `--no-verify`、改快照。
4. 改受保护路径（`.github/`、`.claude/`、`CODEOWNERS`、`evals/baseline/`）未经人批。
5. 没有证据的"已完成"回执。
6. 轮询等待、无尽重试、超预算不升级。
7. 把密钥、`.env`、学生个人信息写进代码/日志/提示词。
