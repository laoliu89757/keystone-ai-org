# 业主意图 INTENT-001：掌握度规则引擎（第一个真任务）

> 提出人：项目负责人（董事会）　日期：2026-10-21
> 处理人：CEO → CPO（转成可测验收标准）→ 首席架构师（定 Schema）→ 算法工程师（实现）→ QA（测试）→ 独立评审官（评审）

## 1 为什么要做这个

这是整个系统的**技术核心**，也是本项目的红线所在：**放行与掌握度判定必须由规则引擎产生，不得由 LLM 决定。**
它还是第一个不需要 PHP / MySQL / 微信环境的模块（本机只有 python + pytest 可用），适合作为编制闭环的首演。

## 2 业主意图（一段话）

学生做完某个知识点的一组练习后，系统要给出三样东西：

1. 该知识点的**掌握度**（0–100 的分数）；
2. **是否放行**进入下一个知识点；
3. **下一步动作建议**（放行 / 巩固 / 复习）。

判定必须**可解释**：每个结论都要能说清"是哪几条规则、各贡献多少分"。任何 LLM 都不参与这个判定。

## 3 技术约束（硬性）

| 约束 | 内容 |
| --- | --- |
| 语言/环境 | Python 3.11，代码放在 `learning-service/` 下 |
| 依赖 | **只用标准库** + 开发期 pytest。禁止 `pip install` 任何第三方包（本机无网络依赖保障） |
| 结构 | 纯函数优先；规则与 I/O 分离；规则参数集中在可读的配置结构里，不得散落魔法数字 |
| 判定输入 | 答题记录列表：知识点 ID、题目难度(1–5)、是否正确、耗时秒 |
| 判定输出 | 掌握度(0–100)、是否放行、理由列表（每条含规则名 + 贡献值/说明）、下一步动作 |
| 默认参数 | 放行阈值 80；最低题量 10；连错临界 3；难度权重随难度递增（具体曲线由架构师定并写进 ADR） |
| 幂等 | 同样的答题集合，重复计算必须得到同样结果（与调用次数、顺序无关；顺序无关性要显式处理） |
| 无副作用 | 不读数据库、不发网络请求、不读系统时间影响判定（时间可作为入参） |
| 换行 | 新文件一律 LF |

## 4 边界情况（必须有用例）

- 0 题、1 题（不足最低题量）
- 全对、全错
- 恰好在阈值上（79.9 / 80.0 / 80.1）
- 高难度题全对 vs 低难度题全对（难度权重必须体现差别）
- 中途连错 ≥3 后转对
- 重复提交同一批答题（幂等）
- 未知知识点 ID / 非法难度值（必须显式报错或返回明确状态，不许静默当 0）
