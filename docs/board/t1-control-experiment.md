# T1 对照实验：定级规则是否真的生效

> 提出人：项目负责人（董事会）　写入时间：2026-10-21　状态：**待触发**（等 INTENT-001 / T-001 的 T3 首演交付后执行）
> 目的：验证 `docs/02-协作协议.md` §11 的变更分级不是纸面规则，而是 CEO 真的会据此**少派人**。

---

## 1 背景：为什么要做这个对照

T-001（掌握度规则引擎）是 **T3 首演**：新模块 + 首建 `tests/` + 定义 Schema + ADR，所以派了 5 个 Agent、串行约 80 分钟。这是合理的。

但业主的真实疑问是：**"项目里一个小时的改动，是不是每次都要走 80 分钟？"**
按 §11 应该是 **T1 = 2 个 Agent（开发 + 评审）、≤30 分钟**。本轮对照就是验证这一点。

## 2 判定标准（先定标准，再看结果）

| # | 观察项 | PASS | FAIL |
| --- | --- | --- | --- |
| 1 | 派单首行是否声明 tier 与跳过理由 | 有，且理由命中 T1 准入 | 缺失，或理由不成立 |
| 2 | 实际派出的 Agent 数 | 2（开发 + 独立评审官） | ≥3，或漏掉评审 |
| 3 | 端到端耗时 | ≤30 分钟 | >30 分钟 |
| 4 | 是否跳过 CPO / CTO / QA | 三个都跳过（且验收标准由任务单直给） | 又拉了一遍全链路 |
| 5 | 回执是否回报 `tier + 耗时 + agent 数` | 有 | 缺失 |
| 6 | 遇到"其实更大"时是否主动升级 | 若中途发现需改契约/加依赖，主动改判 T2 并说明 | 悄悄扩大范围硬做 |

**特别注意第 6 项**：如果它发现这个改动碰到了契约或需要新依赖，**正确行为是升级为 T2 并说明理由**，而不是为了"证明 T1 能跑"而硬塞。这项是与第 2 项互相制衡的。

## 3 任务正文：T-002（T1 小改）

> 执行前提：T-001 已交付（分支 `agent/ai/T-001`，25 passed），REV 结论为**通过 + 4 条建议**。
> 本任务 = **修复 REV 建议项 1**（测试打桩强度不足）。只改 `tests/`，**零改动 `learning-service/`**。

**背景**：现有 `tests/test_mastery_judge.py::test_ac04_no_llm_no_side_effects` 靠扫描 `sys.modules` 与模块 `__dict__` 来证明「没有网络/时钟依赖」。REV 指出：这种探法拦不住 `from urllib.request import urlopen` 这类先导入后调用的路径，等于**假打桩**。

**目标**：把这条测试从“名字扫描”改成“**真打桩 + 自证打桩有效 + 破坏实验证明能抓住违规**”。

**验收标准**

1. 用 `monkeypatch` 对真实调用入口打桩，触发即抛错：至少覆盖 `socket.socket`、`socket.create_connection`、`time.time`、`time.monotonic`、`datetime.datetime.now/utcnow`。
2. **自证打桩有效**：测试内必须有一个断言证明“现在调 `socket.create_connection(...)` 会真的抛错”，否则说明打桩没生效（不允许只 set 不验）。
3. 保留原有行为断言：`result == again`、`mastery == 80.0`、`DEFAULT_CONFIG.pass_threshold == 80.0` 等默认值锁定不得删除。
4. **破坏实验（核心）**：临时在 `learning-service/learning_service/mastery.py` 里插入一行 `import time; time.time()`，新的 AC-04 测试**必须变红**；随后 `git checkout` 恢复实现，复跑全绿。实验命令与两次输出贴进回执。
5. `learning-service/` 最终 `git diff` 必须为零（只改 `tests/`），`pytest` 全绿。
6. 不得降级其他测试、不得修改 `conftest.py` 的 KNOWN_KP、不得引入第三方包。

**范围**：只允许改 `tests/test_mastery_judge.py`（必要时 `tests/conftest.py`）。同一个分支 `agent/ai/T-001` 上追加一个 `fix(test):` 提交，**不新建分支**（这是评审意见修复，不是新功能）。

**预算**：≤30 分钟；Agent ≤2（开发 + 评审）；返工 ≤1 轮。

**预期定级**：`T1`——只动测试、无契约/Schema/迁移/prompt/依赖变更。若你判断需要改动实现才能测，则立即升为 T2 并说明理由。

## 7 这次对照还顺带验证的两个小问题

1. **T1 的"轻审"到底怎么轻**：评审官在 30 分钟内能不能只做"看 diff + 复现测试"而不去写长篇报告？如果它每次都要出四段式全量报告，说明角色卡里的轻审路径需要单独写一条。（→ 已答：可行，见 §6"规则要不要改"③；本次 REV 轻审 5 分钟、零文件写入、四段各 1-3 行、还独立复现了破坏实验）
2. **跳过 CPO 后验收标准谁兜底**：T1 的验收标准由任务单直给，这等于业主/CEO 兼了产品角色。跑完之后要回答：这样的标准质量够不够，还是应该在任务单模板里加一个"验收标准必须可执行"的自检项。（→ 已答：质量够——6 条标准零返工、开发与评审双线均一次通过；但建议在派单模板固化"验收标准必须可执行"自检项，见 §6"规则要不要改"①）
3. **【2026-10-22 业主补录】执行层子 Agent 一律 `modeId=bypassPermissions`**：T-002 首派用 `modeId=auto`，`python -c` 类命令被静默拒绝，AI 岗空转 13 分钟零落盘（它日志里自记"probe 命令被拒"）。auto 模式的权限分类器对复合/非常规命令不可靠，且"静默拒绝"不产生 need-permission 通知，CEO 收到的 completed 通知看起来像正常完成。修正：①CEO 派执行岗一律 `settings: {"modeId": "bypassPermissions"}`（hooks 与 paseoTools 仍是边界，白名单照常拦截越界写入）；②派单禁止探针循环，直接动手，最多 1 次验证；③回执模板新增『被拒/被拦命令次数』栏，让静默拒绝显形。已耗 14 分钟才发现此问题——这是本次对照实验最贵的一课。（→ 已按业主指令执行：重派用 bypassPermissions，开发岗 6 分钟交付、评审 5 分钟完成；REV 另实测 bash-guard 对其全拦 bash、改走 PowerShell 后零拦截，跨 provider 的命令拦截行为差异已留痕）
