## 1 一句话范围

学生完成某个知识点的一组练习并提交后，规则引擎对该组答题记录判定，给出三样东西：

1. 该知识点的**掌握度**（0–100 的分数）；
2. **是否放行**进入下一个知识点；
3. **下一步动作建议**（放行 / 巩固 / 复习三者之一）。

每个结论必须**可解释**：能说清"是哪几条规则、各贡献多少分"。

## 2 用户故事（四要素：谁 / 何时 / 要什么 / 为什么）

### US-1 看到掌握度

| 要素 | 内容 |
| --- | --- |
| 谁 | 学生 |
| 何时 | 完成某个知识点的一组练习并提交后 |
| 要什么 | 看到该知识点当前的掌握度（0–100 分） |
| 为什么 | 知道自己学得是否扎实，而不是只凭感觉 |

对应标准：AC-01、AC-03、AC-09、AC-10

### US-2 知道能否进入下一知识点

| 要素 | 内容 |
| --- | --- |
| 谁 | 学生 |
| 何时 | 该组练习判定完成时 |
| 要什么 | 明确的"是否放行"结论 |
| 为什么 | 学习路径的推进需要客观门槛，而不是"觉得可以了" |

对应标准：AC-02、AC-11

### US-3 得到下一步建议

| 要素 | 内容 |
| --- | --- |
| 谁 | 学生 |
| 何时 | 未达到放行标准时 |
| 要什么 | "巩固"或"复习"的明确动作建议 |
| 为什么 | 知道下一步该练什么，而不是只看到"没通过" |

对应标准：AC-01、AC-02、AC-13

### US-4 判定可解释、可核对

| 要素 | 内容 |
| --- | --- |
| 谁 | 教师 / 家长 / 学生本人 |
| 何时 | 查看任何一个判定结论时 |
| 要什么 | 每条结论背后的规则明细（规则名 + 贡献值/说明） |
| 为什么 | 判定必须可信任、可核对，不能是黑箱；红线要求 LLM 不参与判定 |

对应标准：AC-03、AC-04、AC-05

### US-5 异常数据不静默（接入方视角）

| 要素 | 内容 |
| --- | --- |
| 谁 | 引擎的接入方（学习服务内部调用方，最终服务于学生） |
| 何时 | 重复提交同一批答题记录，或传入未知知识点 ID / 非法难度值时 |
| 要什么 | 幂等的结果；对异常数据的显式报错或明确错误状态 |
| 为什么 | 第一时间暴露数据问题，避免静默错误结果流入学生界面；重复提交不得产生不同结论 |

对应标准：AC-06、AC-07、AC-08、AC-14、AC-15、AC-16

## 3 验收标准

> 约定：**判定输入**为一组答题记录，每条含知识点 ID、题目难度（1–5）、是否正确、耗时秒（INTENT-001 §3）。
> 测试文件名为**建议命名**，QA 可合并或改名；但每条标准的**断言性质与"失败的样子"不得缺失**。
> 错误的具体契约形式（抛异常还是错误状态结构）由首席架构师定（见第 6 节），QA 按实现后的契约断言。

### 组 A：输出契约（主链功能）

**AC-01 判定输出完整**
- Given/When/Then：给定一组合法答题记录（题量 ≥ 最低题量 10）进行判定，输出必须同时包含：掌握度（0–100 的数值）、是否放行（布尔）、下一步动作（"放行/巩固/复习"三者之一）、理由列表（非空，每条含规则名 + 贡献值/说明）。
- 判定方式：`tests/test_mastery_engine.py::test_output_contract_complete` — 结构断言：四要素齐全、0 ≤ 掌握度 ≤ 100、动作 ∈ 三值集合、理由条目结构完整。
- 失败的样子：输出缺"下一步动作"字段；或掌握度为 105；或理由列表为空。

**AC-02 放行与动作一致**
- Given/When/Then：任意一组输入，"是否放行"与"下一步动作"必须逻辑一致：放行为真 ⇔ 动作 = 放行；放行为假 ⇒ 动作 ∈ {巩固, 复习}。
- 判定方式：`tests/test_mastery_engine.py::test_pass_and_action_consistent` — 遍历多组代表性输入断言一致性。
- 失败的样子：放行 = true 而动作 = "复习"；或放行 = false 而动作 = "放行"。

**AC-03 结论可解释**
- Given/When/Then：任意一个输出结论（掌握度、放行、动作），都能对应到理由列表中的具体规则条目，每条理由含规则名与贡献值/说明；不存在"只有一句综合得分、说不出规则明细"的黑箱输出。
- 判定方式：`tests/test_mastery_engine.py::test_reasons_reference_rules` — 断言理由条目非空、规则名非空、贡献值可解析或说明非空；辅以人工走查（评审官/产品核对可读性）。
- 失败的样子：理由列表只有"综合得 85 分"一句，说不出哪几条规则各贡献多少。

### 组 B：判定红线（P0，违反即整体否决）

**AC-04 LLM 不参与判定**
- Given/When/Then：判定的全部过程不调用任何 LLM / 模型网关；判定结果只由规则产生。
- 判定方式：`tests/test_mastery_purity.py::test_no_llm_in_judgment` — 对模型/网络客户端打桩（一旦被调用即抛错），断言判定仍正常完成且结果不变；辅以评审官代码走查确认实现为规则引擎。
- 失败的样子：打桩后判定失败，或判定结果随模型输出变化——说明判定依赖了 LLM。

**AC-05 无副作用**
- Given/When/Then：判定过程不读数据库、不发网络请求、不读系统时钟（时间只能作为入参传入）。
- 判定方式：`tests/test_mastery_purity.py::test_no_side_effects` — 对数据库连接、socket、系统时间函数打桩（触发即抛错），断言判定正常完成。
- 失败的样子：打桩后判定抛错——说明判定过程触发了被禁资源（如内部调用了当前时间）。

**AC-06 确定性**
- Given/When/Then：同一批答题记录、相同入参，任意多次调用，输出完全一致。
- 判定方式：`tests/test_mastery_idempotency.py::test_deterministic_repeated_calls` — 同一输入连续调用 ≥ 3 次，断言结果深度相等。
- 失败的样子：第二次调用的掌握度比第一次多 1 分。

### 组 C：边界情况（10 条，覆盖 INTENT-001 §4 全部 8 项，映射见第 4 节矩阵）

**AC-07 零题（不足最低题量）**
- Given/When/Then：给定空答题记录列表，输出必须是"数据不足"类的明确状态：不得放行；掌握度结果必须可被程序区分于"已测量"的正常结果（为空/未定义，或带"数据不足"标记——具体形式按架构师契约）；理由须说明题量不足最低要求（10 题）。
- 判定方式：`tests/test_mastery_boundary.py::test_zero_records` — 断言不放行 + 数据不足标记 + 理由含题量说明。
- 失败的样子：0 题输入返回一个 0–100 的分数且结构与正常结果无法区分，调用方分不清"没考过"和"全错"。

**AC-08 单题（不足最低题量）**
- Given/When/Then：给定 1 条答题记录（无论对错），处理性质与 AC-07 相同：数据不足、不得放行。
- 判定方式：`tests/test_mastery_boundary.py::test_single_record` — 断言同 AC-07 性质。
- 失败的样子：1 题全对被判放行进入下一知识点。

**AC-09 全对是同条件最高档**
- Given/When/Then：题量 ≥ 10 且全部答对时，掌握度必须高于"其余条件相同（题量、难度分布、耗时）但部分答错"的情形（如错 1 题、错一半）。注：全对是否达到放行阈值取决于难度权重曲线（架构师 ADR 定），本需求不强制"全对必放行"，只强制此比较性质。
- 判定方式：`tests/test_mastery_engine.py::test_all_correct_is_highest` — 同条件下断言 全对 > 错 1 题 > 错一半。
- 失败的样子：全对的掌握度低于错 1 题的掌握度（规则或权重写反）。

**AC-10 全错是同条件最低档且不放行**
- Given/When/Then：题量 ≥ 10 且全部答错时，掌握度必须低于"其余条件相同但至少答对 1 题"的任何情形，且不得放行（动作 ∈ {巩固, 复习}）。
- 判定方式：`tests/test_mastery_engine.py::test_all_wrong_is_lowest` — 同条件下断言 全错 < 对 1 题，且不放行。
- 失败的样子：全错得 50 分并被判放行。

**AC-11 放行阈值为"≥ 80 含端点"**
- Given/When/Then：放行判定条件是掌握度 ≥ 80（含 80.0 本身）：79.9 → 不放行；80.0 → 放行；80.1 → 放行。（INTENT-001 §3 默认参数"放行阈值 80"；含端点是产品决策。）
- 判定方式：`tests/test_mastery_boundary.py::test_threshold_boundary_direction` — 断言三个分数的放行方向性，其中 79.9 与 80.0 的结论必须不同。
- 失败的样子：80.0 被判不放行（阈值被实现成开区间），或 79.9 与 80.1 方向颠倒。
- 备注：边界分数的测试构造依赖计分曲线，实现定稿后由 QA 与算法工程师商定构造方式（若曲线产生离散分数，则以最接近 80 两侧的可构造分数验证方向性）；"80.0 必须放行"的语义本身不可协商。

**AC-12 难度权重差异（高难全对 > 低难全对）**
- Given/When/Then：题量相同、全部答对、仅难度分布不同时，难度 5 全对的掌握度必须**严格大于**难度 1 全对的掌握度。（INTENT-001 §3：难度权重随难度递增，具体曲线由架构师定并写进 ADR。）
- 判定方式：`tests/test_mastery_engine.py::test_high_difficulty_beats_low_difficulty` — 断言严格大于（不允许相等）。
- 失败的样子：两组分数相等（权重未生效），或高难全对反而更低。
- 备注：QA 可加测 难度 3 > 难度 1、难度 5 > 难度 3（递增性）。

**AC-13 连错 ≥3 后转对**
- Given/When/Then：给定一组题量 ≥ 10、中途连续答错 ≥ 3、之后答对的记录，则：(a) 理由列表中必须存在与"连错"相关的规则条目（连错临界 3 的信号不得被吞掉）；(b) 在总题量与总正确数相同的前提下，含连错段的结果，其掌握度**不得高于**无连错段的结果（连错为负向信号，具体扣分幅度由架构师定）；(c) 结果可复现（同输入同输出）。
- 判定方式：`tests/test_mastery_boundary.py::test_consecutive_wrong_then_recover` — 双序列对比断言 + 理由结构断言（示例序列：`对对错错错对对对对对` vs `对对对对对错对对错错`，同为 7 对 3 错）。
- 失败的样子：理由列表里没有任何连错相关条目（"连错临界 3"参数形同虚设）；或含连错段的一组反而得分更高。
- 备注：转对后"下一步动作"的具体取值由规则设计决定（架构师 ADR），本需求只约束上述三条性质。

**AC-14 幂等与顺序无关**
- Given/When/Then：同一批答题记录重复提交，结果完全一致；且同一**集合**以不同顺序输入，结果也必须完全一致（顺序无关性要显式处理，不得隐含依赖输入先后）。
- 判定方式：`tests/test_mastery_idempotency.py::test_idempotent_and_order_insensitive` — 同输入调用两次 + 打乱记录顺序后调用，断言结果深度相等。
- 失败的样子：打乱答题记录的先后顺序后掌握度改变了。

**AC-15 未知知识点 ID 显式报错**
- Given/When/Then：记录中含有系统未登记的知识点 ID 时，必须显式报错或返回明确错误状态，**绝不静默处理**——既不许当作 0 分，也不许当作普通知识点照常计算。
- 判定方式：`tests/test_mastery_boundary.py::test_unknown_knowledge_point_rejected` — 断言结果可被程序明确区分于正常结果（抛异常，或返回带错误标记的状态）。
- 失败的样子：未知 ID 被静默接受并算出一个正常分数。

**AC-16 非法难度值显式报错**
- Given/When/Then：题目难度超出 1–5（如 0、6、负数、非数值）时，必须显式报错或返回明确错误状态，**绝不静默当 0、截断或夹取**。
- 判定方式：`tests/test_mastery_boundary.py::test_invalid_difficulty_rejected` — 参数化遍历非法难度值，逐个断言显式错误。
- 失败的样子：难度 6 被静默按某个有效值计算且无任何错误标记。

## 5 非目标（本次明确不做）

1. **LLM 参与判定或讲解**：本模块判定与 LLM 完全无关（红线）；讲解/出题/批改/错因诊断属于其他模块。
2. **数据库读写**：引擎不感知任何存储。
3. **网络请求**：不调模型网关、不调远程服务。
4. **系统时间读取**：时间只能作为入参，引擎不得自行读时钟。
5. **前端渲染 / 界面**：展示是前端任务，本需求只约束引擎输出。
6. **PHP 业务后台对接**：本模块在 `learning-service/` 内独立成型，不涉及 FastAdmin。
7. **多知识点联合判定 / 学习路径规划**：只对"单个知识点的一组练习"判定。
8. **耗时真实性校验 / 防作弊**：耗时仅作为入参，不校验其真伪。
9. **掌握度纵向建模**：不做历史趋势、多次练习的进步曲线，只针对本次提交的这组记录。
10. **难度权重公式与参数取值**：曲线、阈值以外的参数调优由首席架构师定并写进 ADR，本需求只约定可测性质。
11. **性能优化与并发**：只要求纯函数、可重入、确定性，不设性能指标。

## 6 待架构师确认项（本需求不暗含技术决策）

| # | 事项 | 说明 |

## 7 合规说明

- 本文档**不含任何学生个人信息**；所有示例均为抽象序列（如"对对错错错对对对对对"）。
- 本模块无新增学生数据出口（无存储、无网络）；生产环境处理学生答题记录时按章程通用规则执行（测试用合成数据、日志不含学生个人信息）。
- 不涉及支付、平台审核，**无需合规官会签**；如评审官认为需要，可在评审意见中提出。

## 8 下游使用说明

- **首席架构师**：据第 6 节定 Schema 与 ADR；ADR 中登记本文件版本（v1.0）作为依据。
- **算法工程师**：按 AC-01～AC-16 实现，自测覆盖组 A/B/C。
- **QA**：按第 3 节各条"判定方式"建测试；测试文件名可调，断言性质不可缺；核心规则分支全覆盖（INTENT-001 §5）。
- **独立评审官**：按本文件逐条核对"是否满足验收标准"，并重点核查组 B 三条红线。
